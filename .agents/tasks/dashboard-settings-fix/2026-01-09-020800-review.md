# Dashboard and settings UI restoration

Three UI issues were fixed: activity tab numbers now change when switching between Day/Week/Month tabs (showing 14 days, 8 weeks, 6 months respectively), recent digests display with thumbnails and descriptions matching the lecture card format, and the Change Password section was restored to the Settings page with full validation. The backend endpoint was changed from POST to PATCH per requirements, and password history checking was rewritten to prevent timing side-channels.

**Watch for:** Password history check hashes the new password before checking history (confirmed), and the description extraction fallback returns a string constant instead of empty when no content exists (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

Activity tab numbers correctly aggregate dailyActivity data into day/week/month periods and display different totals for each tab (14 days, 8 weeks, 6 months).

Recent digests switched from compact list to grid card layout matching lectures, with thumbnails from the associated lecture, descriptions from digest content (summary or first key takeaway), duration badge overlaying the thumbnail, and hover effects.

Change Password was added to Settings with current/new/confirm fields, client-side validation matching signup requirements, password strength indicator, and PATCH endpoint submission. Form clears on success.

The backend endpoint changed from POST to PATCH and rewrote password history checking to use Promise.all for constant-time comparison against all 5 previous passwords, eliminating the early-return timing side-channel.

## Activity tab aggregation and totals

ActivityAnalytics aggregates dailyActivity data three ways: last 14 days (Day tab), last 8 weeks (Week tab), and last 6 months (Month tab). Each tab displays two stat cards showing total lectures and digests for that period. Week aggregation groups by ISO week number, month by year-month. Totals correctly reduce the aggregated data. Switching tabs updates the numbers because each TabsContent renders renderStatsCards with different totals and labels.

## Recent digests card redesign

DigestCard was rewritten from horizontal compact layout to vertical card matching LectureCard. Structure: thumbnail container (aspect-video) with duration badge overlaid at bottom-right, content section with title, description, date, and hover arrow.

Thumbnail comes from the associated lecture (thumbnail_url or thumbnailUrl). If missing, a Clapperboard icon placeholder renders.

getDescription tries content.summary first, then the first item in keyTakeaways or key_takeaways arrays. If no content exists, returns "Video digest". This fallback misleads when a digest truly has no content—empty string or omitting the description element would be clearer.

Hover effect changes title color to primary and fades in "Open →" label (opacity-0 group-hover:opacity-100).

## Change Password section in Settings

Settings now includes a card with Lock icon header, three password fields (current, new, confirm), password strength indicator below new password field, and submit button.

Client-side validation: all three fields required, new password passes validatePassword, new matches confirm, new differs from current. Validation errors show as toast notifications.

On submit, calls base44.patch('/auth/change-password') with currentPassword and newPassword. Success clears form and shows success toast. Errors show server message in destructive toast.

## Backend endpoint method and password history

Endpoint changed from router.post to router.patch, matching task requirement. Frontend updated to base44.patch.

Password history check rewritten to eliminate timing side-channels. Previously looped through passwordHistory with early return on first match, creating timing leak. New implementation collects all hashes (current password plus up to 4 from passwordHistory), runs Promise.all to compare new password against all in parallel, then checks if any matched. Ensures constant time regardless of match position.

However, the code hashes the new password before checking password history. If history check fails, that hash is discarded and CPU was wasted. Hash should be computed after history check passes.

Password history correctly maintained: current password prepended to passwordHistory, array sliced to 5 entries (current + 4 previous).
